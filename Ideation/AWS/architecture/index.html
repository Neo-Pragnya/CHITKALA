CHITKALA on AWS — optional cloud services around a local-first core

The vault on the user's device stays canonical. Every AWS service is opt-in, has a local substitute, and never writes to the vault.

The numbered steps
#From → toWhat happens
1Author → CHITKALA desktopThe author works fully offline: the Markdown vault on disk is canonical; editing, links, graph and FTS5 search never need AWS.
2CHITKALA desktop → Amazon CognitoIf the author opts in, they sign in and the device is registered; Cognito issues short-lived JWTs.
3CHITKALA desktop → API GatewayThe desktop calls the /v1 API with its JWT; AWS WAF filters abuse at the edge.
4API Gateway → API handlersAPI Lambdas re-check every capability grant: the same rules as the desktop's policy broker.
5API handlers → DynamoDBTenant-scoped records (devices, grants, runs, audit index) are keyed by tenant in DynamoDB.
6DynamoDB → AWS KMSEach tenant's data is encrypted with its own KMS key.
7AWS KMS → CloudWatch · X-RayKey use is logged in CloudTrail; metrics and traces carry correlation ids, never document bodies or prompts.
8API handlers → Model relayFor a grounded question, the desktop retrieves locally and sends only the scope-filtered context; the relay checks consent and budget.
9Model relay → Amazon BedrockBedrock answers through Guardrails; the answer may cite only the chunk ids it was given.
10API handlers → IndexerFor the web companion, consented folders (and only those) are queued for hosted indexing.
11Indexer → Amazon BedrockThe indexer chunks by heading and asks Bedrock for embeddings, recording the model and version.
12Indexer → Aurora PostgreSQLChunks, vectors, FTS fields and link edges are written to Aurora with row-level tenant security.
13Model relay → Aurora PostgreSQLHosted questions use hybrid retrieval (vector + full text + graph) from Aurora before the model call.
14API handlers → Step FunctionsA long-running or scheduled skill starts a Step Functions agent run with its grants and budgets.
15Step Functions → Amazon BedrockPlanner and writer steps call Bedrock within the run's token and time budget.
16Step Functions → Tool sandboxTools run in an isolated Fargate task: no internet, VPC endpoints only, hard timeouts.
17Step Functions → API GatewayThe run ends as a patch proposal pushed to the desktop over WebSocket; the run waits for review.
18CHITKALA desktop → API GatewayThe author reviews the diff; the desktop commits it locally (compare-and-swap) and the run resumes. The cloud never writes the vault.
19CHITKALA desktop → Publish bucketTo publish, only allowlisted, sanitized files are uploaded as a bundle (presigned URL).
20Publish bucket → Astro buildAn isolated CodeBuild project builds the Astro site and runs the privacy, link and CSP checks.
21Publish bucket → Amazon CloudFrontAfter the author approves the preview, CloudFront switches to that build (rollback = previous build).
22Amazon CloudFront → Public readersReaders get the public-only site, search index and graph.
23CHITKALA desktop → Sync objectsSync: the desktop encrypts committed revisions locally and uploads content-addressed ciphertext.
24Sync objects → Other deviceThe other device is notified, fetches, verifies and decrypts, then reconciles locally (fast-forward, merge or conflict copy).

Encrypted personal sync — the relay stores ciphertext it cannot read

Devices encrypt with a vault key held in their OS keychain. S3 holds immutable content-addressed objects; DynamoDB holds the revision head as a compare-and-swap.

The numbered steps
#From → toWhat happens
1Device A → HTTP APIDevice A commits locally, then asks to push: parent sequence number plus the hashes of its encrypted objects.
2HTTP API → Sync APIThe Sync API checks the device's JWT and its grant on this vault.
3Sync API → Revision ledgerIt reads the vault head and returns presigned PUT URLs only for objects the bucket does not have yet.
4Device A → Sync bucketDevice A uploads ciphertext objects and the encrypted manifest with If-None-Match: immutable and deduplicated.
5Sync API → Revision ledgerCommit is a conditional update: head = parent + 1 only if head is still the parent. Nobody silently wins.
6Sync API → HTTP APIIf another device moved the head first, the push gets 409: Device A fetches, merges locally and retries.
7Revision ledger → NotifierThe head change flows through DynamoDB Streams to the notifier.
8Notifier → WebSocket APIThe notifier posts 'head advanced' (ids only, no content) to the vault's other device connections.
9WebSocket API → Device BDevice B is woken up over its WebSocket.
10Device B → Sync bucketDevice B fetches the manifest and objects by presigned GET, checks every hash and decrypts with the vault key.
11Device B → Reconcile + reindexIt reconciles locally: fast-forward, three-way merge, or a named conflict copy; then reindexes. No silent data loss.
12Sync bucket → AWS KMSAt rest, S3 and DynamoDB add SSE-KMS with the tenant key: a second layer, not the confidentiality guarantee.
13Revision ledger → AWS BackupPoint-in-time recovery, AWS Backup plans and S3 versioning make the replica restorable.

Grounded intelligence on AWS — relay mode and hosted-index mode

Relay (default cloud mode): the desktop retrieves locally and sends only consented context. Hosted index: opt-in folders indexed in Aurora (private subnets, no NAT, VPC endpoints).

The numbered steps
#From → toWhat happens
1CHITKALA desktop → API GatewayRelay mode: the desktop retrieves locally (FTS5 + vectors + graph), filters by scope, redacts, and sends question + context.
2API Gateway → Model relayThe relay receives the request with the user's JWT.
3Model relay → Consent & budgetsIt checks the vault's consent mode, the model allowlist and the remaining token budget (atomic counter).
4Model relay → Bedrock GuardrailsGuardrails screen the assembled context for prompt attacks and sensitive data before any model call.
5Bedrock Guardrails → Bedrock modelsThe model (chosen by family, with a fallback order) answers, citing only the chunk ids it was given.
6API Gateway → CHITKALA desktopThe answer streams back; the desktop's verifier resolves each citation to revision + span and flags unsupported claims.
7CHITKALA desktop → Consented corpusHosted index (opt-in): only consented folders are uploaded, encrypted with the tenant's KMS key. Excluded paths never leave.
8Consented corpus → Index queueEach object event is queued, with retries and a dead-letter queue.
9Index queue → IndexerThe indexer chunks by heading (about 350–650 tokens) with stable anchors: document + section + span + hash.
10Indexer → Bedrock modelsEmbeddings come from Bedrock over a VPC endpoint; model id and version are recorded (a new model = a new namespace).
11Indexer → Aurora PostgreSQLChunks, tsvector, vectors and link edges are upserted in one transaction; obsolete chunks are removed.
12Web companion → API GatewayWeb companion: the user asks a question through the same API and JWT.
13Model relay → RetrieverIn hosted mode the relay asks the retriever instead of receiving context from a device.
14Retriever → Aurora PostgreSQLLexical, vector and graph channels run separately under row-level security, then fuse with RRF and an optional rerank; then steps 4–5 run.
15CHITKALA desktop → Consented corpusRevoking consent deletes the objects and propagates to chunks, vectors and summaries.

A cloud agent run — bounded, brokered, and finished by a human

Step Functions is the run state machine (CREATED → … → COMPLETED). Tools go through a policy broker; the result is a patch proposal the desktop commits.

The numbered steps
#From → toWhat happens
1CHITKALA desktop → API GatewayThe author starts a skill: POST /v1/agent-runs with skill id, scopes, budgets and an idempotency key.
2API Gateway → Run starterThe starter validates the skill manifest; skill prose can never widen permissions.
3Run starter → Grants · runs · eventsIt loads grants (principal + action + scope + expiry). Anything not granted is denied.
4CHITKALA desktop → Run context packWithout a hosted index, the desktop uploads a context pack: only in-scope documents, deleted when the run ends.
5Run starter → Step FunctionsStartExecution is named by the idempotency key, so a retry never starts a second run.
6Step Functions → Amazon BedrockPlanner and writer steps call Bedrock; the budget is checked before each call.
7Step Functions → Run context packThe run reads only its context pack (or the consented hosted index).
8Step Functions → Policy brokerEvery tool call goes through the broker: schema, grant, quota and timeout.
9Policy broker → Tool sandboxCode tools run as a Fargate task: isolated subnet, no internet, CPU/memory/time caps.
10Policy broker → MCP adapterMCP tools go through an adapter that enforces a destination allowlist.
11MCP adapter → Remote MCP serversTool results come back tagged untrusted and are sanitized before the model sees them.
12Step Functions → Proposals · auditThe draft becomes a patch proposal: diff, base revision, evidence and a provenance label per paragraph.
13Step Functions → API GatewayThe run waits on a task token; 'approval required' is pushed to the desktop over WebSocket.
14CHITKALA desktop → API GatewayThe author approves the exact patch hash; the desktop commits it with compare-and-swap and reindexes.
15API Gateway → Step FunctionsThe committed revision resumes the run (SendTaskSuccess). Reject or timeout ends it as REJECTED or EXPIRED.
16Step Functions → Proposals · auditThe outcome, grants used, tools called and sources read are appended to the audit log.

Managed publishing — only allowlisted files leave the device

Static export to GitHub Pages or a folder stays free and local. The managed path builds in a VPC with no NAT and no vault access, scans again, and promotes by pointer.

Trust zones, local and cloud — authority lives in grants, not in text

The desktop core is the only writer of the vault. AWS services receive consented data, are confined per tenant, and send back only proposals.

The numbered steps
#From → toWhat happens
1Zone 3 · Untrusted content → Zones 1–2 · Trusted core + UIContent enters the core as data: parsed, sanitized and rendered in an isolated origin.
2Zone 4 · Untrusted extensions → Zones 1–2 · Trusted core + UIExtensions ask the policy broker; a grant (principal + action + scope + expiry) decides.
3Zones 1–2 · Trusted core + UI → Zone 5 · AWS edgeOnly consented, scope-filtered data leaves the device, with a short-lived device JWT.
4Zone 5 · AWS edge → Tenant isolationAPI handlers assume a tenant-tagged session; IAM, KMS and row-level security confine each tenant.
5Tenant isolation → Execution isolationAgent tools and site builds run isolated, with no route back to devices.
6Execution isolation → Zones 1–2 · Trusted core + UIResults come back only as patch proposals the author reviews and the core commits.
7Zone 3 · Untrusted content → NeverInjected text asking for tools or uploads gets nothing: it holds no grant.

Delivery — open-source CI, multi-account AWS, signed desktop releases

No long-lived AWS keys in CI. Infrastructure is CDK; the same artifacts move staging → production; desktop updates are signature-checked.
